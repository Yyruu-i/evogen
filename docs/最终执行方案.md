## 二、耦合点解决方案

### 2.1 P1 认证（JWT）与 P2 隔离（user_id）的耦合

**问题：** JWT 里存的 `sub` 字段是 `user_id`。后端所有隔离查询依赖从 JWT 提取的 `user_id`。两者是否冲突？

**答案：不冲突，天然耦合且互补。**

```
用户登录 → POST /auth/login → 返回 JWT（payload: {sub: user_id, exp: ...}）
         ↓
前端存 JWT → 所有 API 请求带 Authorization: Bearer <JWT>
         ↓
后端 get_current_user() Depends → 从 JWT 解码 user_id → 传入 engine/DAO 层
         ↓
隔离查询: SELECT ... FROM sessions WHERE user_id=? AND ...
```

**关键设计点：**
- `get_current_user()` 依赖只做**解码验证**，不查数据库（JWT 自包含），性能无损
- session 机制不变 — `sessions` 表新增 `user_id` 列后，`list_sessions` 自然隔离
- 旧数据（user_id = 'default'）在未登录时/迁移前可访问，登录后不可见 → 这是**预期行为**

### 2.2 PersonaEngine / MemoryEngine 全局单例改造

**问题：** 当前 `persona/engine.py:314-322` 和 `memory/engine.py` 都是全局单例 `_engine`。per-user 隔离后不能继续用全局单例。

**方案：线程安全 per-user 实例池**

```python
# backend/persona/engine.py 改造伪代码
_engines: dict[str, PersonaEngine] = {}
_lock = threading.Lock()

def get_engine(user_id: str = "default") -> PersonaEngine:
    if user_id not in _engines:
        with _lock:
            if user_id not in _engines:
                _engines[user_id] = PersonaEngine(user_id=user_id)
    return _engines[user_id]
```

**影响评估：**
- FastAPI 每个请求可能在不同线程，per-user 实例池 + user_id 参数确保隔离
- **不阻塞认证流程** — `PersonaEngine` 的 `user_id` 是在 API 路由层从 JWT 解出后传入的，不依赖 engine 自身做认证
- MemoryEngine 同理改造

### 2.3 Schema 迁移能否在 P1 一次性完成？

**可以且应该。**

推荐方案：**一个 migration 文件完成所有 DDL 变更**

```sql
-- backend/db/migration_v0.2.0_auth.sql

-- 1) users 表（P1 需要）
CREATE TABLE IF NOT EXISTS users (...);

-- 2) 所有业务表加 user_id 列（P2 需要）
ALTER TABLE sessions ADD COLUMN user_id TEXT NOT NULL DEFAULT 'default';
ALTER TABLE memory_facts ADD COLUMN user_id TEXT NOT NULL DEFAULT 'default';
ALTER TABLE experience_trajectories ADD COLUMN user_id TEXT NOT NULL DEFAULT 'default';
ALTER TABLE experience_feedback ADD COLUMN user_id TEXT NOT NULL DEFAULT 'default';

-- 3) persona_attributes 改主键为 (user_id, key)
--    先删旧表重建（因为 SQLite 不支持 ALTER TABLE 改主键）
CREATE TABLE persona_attributes_new (
    user_id  TEXT NOT NULL DEFAULT 'default',
    key      TEXT NOT NULL,
    value_json TEXT NOT NULL,
    updated_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (user_id, key)
);
INSERT INTO persona_attributes_new SELECT 'default', key, value_json, updated_at FROM persona_attributes;
DROP TABLE persona_attributes;
ALTER TABLE persona_attributes_new RENAME TO persona_attributes;

-- 4) 索引
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);
CREATE INDEX IF NOT EXISTS idx_memory_user ON memory_facts(user_id);
CREATE INDEX IF NOT EXISTS idx_experience_user ON experience_trajectories(user_id);
```

**为什么在 P1 一次性做：**
- `ALTER TABLE ADD COLUMN ... DEFAULT 'default'` 对已有数据零影响
- 避免 P1→P2 间再做一次 migration，减少 downtime
- `persona_attributes` 主键改造必须一次到位，拆分反而会造成 P1→P2 间的数据不一致

### 2.4 Chroma 向量隔离

**问题：** Chroma collection 已存有旧向量数据，无 `user_id` metadata。

**方案：**
1. 新数据写入时注入 `metadata={"user_id": user_id}`（无侵入）
2. 查询时加 `where={"user_id": user_id}` 过滤
3. 旧数据（无 user_id metadata）在 per-user 查询中**不可见** — 这是预期行为，旧数据可通过后台脚本一次性回填 user_id

### 2.5 Skills 内置/自定义判断

**问题：** `skills_routes.py` 的 `_scan_skills()` 扫描文件系统，怎么区分内置和用户自定义？

**方案：**
- 内置技能路径：`~/.hermes/skills/{category}/`（无 user_id 层级）
- 用户自定义技能路径：`~/.hermes/skills/{user_id}/{category}/`
- `_scan_skills()` 返回时标记 `scope: 'builtin' | 'user'`
- 前端：内置技能不显示编辑/删除按钮
